Per-distro operational subkeys — sign packages + repository metadata
--------------------------------------------------------------------
One subkey per distribution line, not per released version: the same subkey
signs every version that line has (debian's three suites, fedora's three
releases, and so on). Rotating a line means replacing one subkey.

This list names each line's CURRENT subkey, which is what a new consumer
should be told. Four of these lines have been rotated, so their published key
file (keys/<line>/qmdmm-packages.gpg) is deliberately bigger than its row
here: it also carries the outgoing subkey, revoked, so that a consumer which
has already refreshed can be told "revoked" instead of "unknown key". Only the
fingerprints above are operational. lab/check-fingerprints.sh is what keeps
this list in step with the key files.

These subkeys are bound to the root key above, so anyone holding the root
public key can attribute their signatures without a new trust anchor.

Repository roots
----------------
Pages serves the gh-pages branch, and what lands there IS the repository
layout: <pages>/<line>/<version> is a repository root a consumer points
straight at. One directory per (line, version) row that stage A built and
stage S signed — twelve of them.

  <pages>/debian/trixie     apt      deb [signed-by=…] <pages>/debian/trixie trixie main
  <pages>/debian/forky      apt      same shape, suite forky
  <pages>/debian/sid        apt      same shape, suite sid
  <pages>/ubuntu/resolute   apt      same shape, suite resolute
  <pages>/ubuntu/stonking   apt      same shape, suite stonking
  <pages>/fedora/44         rpm      baseurl=<pages>/fedora/44
  <pages>/fedora/45         rpm      baseurl=<pages>/fedora/45
  <pages>/fedora/rawhide    rpm      baseurl=<pages>/fedora/rawhide
  <pages>/rocky/10          rpm      baseurl=<pages>/rocky/10
  <pages>/alma/10           rpm      baseurl=<pages>/alma/10
  <pages>/arch/rolling      pacman   Server = <pages>/arch/rolling
  <pages>/manjaro/rolling   pacman   Server = <pages>/manjaro/rolling

Two directories are built OFF-CI — the root secret never enters a workflow —
and publish stages them at their published path:

  <pages>/debian-keyring    keyring source, root-signed. Its InRelease is the
                            one thing only the root key may sign, which is why
                            this source exists separately from the day-to-day
                            one.
  <pages>/debian-revoked    fixture signed by a since-revoked subkey — must be
                            rejected by anything holding the current keys

Two sources, two directories
----------------------------
The keyring source and the day-to-day source cannot share a directory: apt's
Signed-By names one key file per source, and the whole design rests on the
keyring source being verifiable by the root key ALONE. So:

  keys/qmdmm-root.gpg               root public key only (no subkeys)
                                    -> the keyring repo's Signed-By
  keys/<line>/qmdmm-packages.gpg    root public key + that line's subkey
                                    -> the day-to-day repo's Signed-By

Every consumer in this lab takes its keys from <pages>/keys/, which is what a
consumer of a published repository does: there is no other channel.

The revoked fixture key
-----------------------
One key exists only to make revocation measurable, which is why there are two
public files here for it and one for everything else:

  keys/revoked-fixture-before.gpg   the key as it looked BEFORE it was revoked
  keys/revoked-fixture.gpg          the same key, with the revocation certificate

  fingerprint  0B1F 7C5A A6FE 619F D3E7  9A73 E851 6372 7018 1DB8
  keyid        E851637270181DB8
  status       revoked by the root key

Repositories signed by it are published at <pages>/revoked-rpm and
<pages>/revoked-pac. Stage B reads the SAME artifact twice: accepted under the
"before" file, refused under the "after" one. That pair is the whole point -
FINDINGS 3.1 says revocation is only as good as the verifier, and this is how the
lab measures dnf and pacman rather than assuming they behave like gpgv.

The private half is not here and does not enter the repository. It lives in the
`fixture` environment, because the signature has to be made BEFORE the revocation
(gpg will not sign with a revoked key), which is also why the fixture repository
is built at run time instead of being committed.
